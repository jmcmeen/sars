# Contributing to sars

Thanks for your interest. Bug reports, questions, documentation fixes, and
new models are all welcome. This page covers how to get set up, how the
project is organised, and what a change needs before it can be merged.

## Getting help and reporting problems

- **Bugs and feature requests:** open an issue at
  <https://github.com/jmcmeen/sars/issues>. For a bug, include the `sars`
  version (`sars.__version__`), Python version, a minimal DataFrame that
  reproduces it, and the full traceback.
- **Questions about usage or SAR methodology:** also an issue. There is no
  separate mailing list or chat.
- **Security concerns:** email the maintainer directly rather than opening a
  public issue.

The project has one maintainer and no fixed release schedule beyond the
automated one described below. Expect a response to issues within a week.
Decisions about scope and API follow the R `sars` package where it has an
opinion, and otherwise aim for the smallest API that solves the problem.

## Development setup

Only the maintainer can push to this repository, so contributions come in
as pull requests from a fork. Fork
[jmcmeen/sars](https://github.com/jmcmeen/sars) on GitHub, then clone your
fork. The project uses [uv](https://docs.astral.sh/uv/) for environments
and `make` as a thin front end.

```bash
git clone https://github.com/YOUR-USERNAME/sars.git   # your fork
cd sars
git remote add upstream https://github.com/jmcmeen/sars.git
make install        # uv sync --extra dev
make test           # full test suite (coverage is on by default via pyproject)
make lint           # ruff check
make fmt            # ruff format + autofix
make check          # lint, format check, and tests, as CI runs them
```

Without `make`:

```bash
uv sync --extra dev
uv run --extra dev pytest
uv run --extra dev ruff check src tests
uv run --extra dev ruff format src tests
```

CI runs ruff at the version pinned in `uv.lock` and the test suite on
Python 3.10 through 3.15. The dev extra includes the `geo` extra so the
GeoDataFrame tests run locally too.

## Layout

```text
src/sars/
  _models.py      the 20 SAR models, _MODEL_REGISTRY, and the NLS fitting loop
  _inference.py   sar_multi, sar_average, bootstrap_ci, information criteria
  _threshold.py   piecewise (small-island-effect) models
  _io.py          from_csv, from_df, from_geodataframe, from_pyinaturalist, load_galap
  _plots.py       matplotlib helpers
  data/           bundled Galapagos dataset
tests/
  r_reference/    galap.csv and all_models_galap.csv, generated by R
  test_*.py       one file per module
docs/             mkdocs-material site, API pages built from docstrings
paper/            JOSS paper source
```

Public names are re-exported from `sars/__init__.py` and listed in
`__all__`. Modules prefixed with an underscore are private.

## Making a change

1. Open an issue first for anything larger than a typo, so the design can be
   discussed before code is written.
2. In your fork, branch from an up-to-date `main` (`git fetch upstream &&
   git checkout -b my-change --no-track upstream/main`), make the change,
   and add or update tests. New behaviour needs a test; a bug fix needs a
   test that fails without the fix.
3. Add a line under `[Unreleased]` in `CHANGELOG.md` (Keep a Changelog
   format: Added, Changed, Fixed, Removed).
4. Run `make check`.
5. Push the branch to your fork (`git push -u origin my-change`) and open a
   pull request against `main` in this repository. Describe what changed and
   why, and reference the issue.

Merges to `main` that pass CI are released automatically and published to
PyPI, normally as one patch version per merge; merges that land close
together can share a release, and a minor or major bump is triggered by
hand when the maintainer decides one is due. The `[Unreleased]` changelog
entries become the release notes. You do not need to touch version numbers.

## Adding a SAR model

Models are declared, not subclassed. To add one:

1. In `src/sars/_models.py`, register a `_ModelSpec` with the model name,
   the function `f(area, *params)`, parameter names, lower and upper bounds,
   and a start grid (one list of starting values per parameter). The fitting
   loop tries every point in the Cartesian product of the grid, so keep each
   list short and spread across the plausible range.
2. Add the public wrapper `sar_<name>()` next to the others and export it
   from `__init__.py`.
3. If the R `sars` package has the same model, add it to the `models`
   vector in `tests/r_reference/generate_r_reference.R`, rerun the script
   with R `sars` installed, commit the regenerated `all_models_galap.csv`,
   and add the name to `ALL_MODELS` in `tests/test_models.py` so the R
   validation, convergence, and predict tests pick it up.
4. If there is no R counterpart, leave it out of `ALL_MODELS` (the R
   comparison would fail on the missing reference row). Say so in the pull
   request and add a dedicated test that checks convergence and compares
   the fit against a known analytic or published result instead.
5. Document the formula in `docs/models.md` and add the function to
   `docs/api/models.md`.

## Style

- `ruff` handles formatting and import order; run `make fmt` before
  committing.
- Public functions have NumPy-style docstrings; the docs site is built from
  them.
- Keep the arithmetic-space NLS convention and the R-matching log-likelihood
  for information criteria. Changes to either affect every model comparison
  users have published and need an issue and a changelog note.
